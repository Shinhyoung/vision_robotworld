## 1. 프로젝트 한 줄 요약

컨베이어 정지 스테이션에서 MC 나일론 블록 3종을 **EfficientAD로 불량 검사**하고,
양품이면 **FoundationPose로 6D 포즈**를 계산해 **ROS 2로 로봇 부서에 전달**한다.
로봇 제어·grasp·pick&place는 로봇 부서 범위(우리 범위 밖).

원 요구사항은 저장소 루트의 `claude.md`.

## 2. 확정된 전체 프로세스 (2차 협의 반영)

```
컨베이어 ──▶ [벨트 센서가 감지해 정지]   ← 정지 제어는 컨베이어 측 (우리 범위 밖)
                    │
                    ▼   카메라 + 로봇팔 위치
              ① EfficientAD 불량 검사
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   불량 (STATUS_NG)         양품 (STATUS_OK)
        │                       │
   로봇 부서가 벨트 재이동    ② FoundationPose 포즈 계산
   (끝에서 배출)                │
                                ▼
                     로봇 pick & place → 벨트 재이동
```

**확정 사항**
- 정지 스테이션(index) 방식 — 이동 중 실시간 검사 아님
- 벨트 정지는 **컨베이어 센서**가 처리. 우리는 정지 후 트리거만 받음
- 벨트 재이동 명령은 **로봇 부서가 `part_result`의 `status`를 보고 자체 판단**
  → 새 메시지 불필요, 기존 계약으로 충분
- 불량품은 벨트 끝에서 배출
- 스테이션 부품 간 최소 간격 **500 mm**

## 3. 지금 바로 할 작업 (중단된 지점)

### FoundationPose 적용 — 환경 구축부터

포즈는 아직 **`icp`(CPU 참조 구현)**이다. 운영 목표인 FoundationPose 는
미적용이고, 막고 있는 것은 CAD 가 아니라 **환경**이다.

**라이선스 방침 확정**: 공개판(비상업)을 **데모 용도로 사용**한다. 상용화
단계에서 NGC 상업판으로 전환한다.

**CAD 유무는 장벽이 아니다.** FoundationPose 는 메시를 요구할 뿐 출처를 따지지
않는다. `new_part` 는 depth 재구성 메시가 있어 `has_cad=True` 이고, 출하 3종은
CAD 파일이 이미 `01_input/` 에 있다. 즉 **네 부품 모두 지금도 조건을 충족**한다.

실제 장벽:
1. **ROS 2 미설치** — FoundationPose 는 Isaac ROS 컨테이너로 배포되고,
   `FoundationPoseBackend` 는 `ros_bridge` 콜러블을 주입받는 구조다
2. Isaac ROS 컨테이너 + NVIDIA Container Toolkit

전환 자체는 설정 한 줄(`pose.backend`)이다. 부품별로 나누려면 검사와 대칭으로
`parts.<id>.pose_backend` 를 만들면 되지만, 환경이 없으면 어느 부품도 못 간다.

## 4. EfficientAD 실적용 (2026-08-05 세션)

### 4.0 GPU 스택 — 구축 완료

```
torch 2.11.0+cu128   sm_120 포함   RTX 5070 (compute 12.0) 인식
anomalib 2.6.0       (1.x 아님 — API 가 다르다)
```

`--index-url https://download.pytorch.org/whl/cu128` 로 설치하면 sm_120 이
들어 있다. **nightly 채널은 필요 없었다** — §9 에 "첫 관문" 으로 적혀 있던
항목이다.

⚠️ **anomalib 이 `opencv-python-headless` 를 끌어와 GUI cv2 를 덮어쓴다.**
뷰어가 죽으면 `pip install --user --force-reinstall --no-deps opencv-python`.

⚠️ anomalib 이 저장소 루트에 `datasets/`(1.5 GB, ImageNette) 와
`results/`(1 GB) 를 만든다. `.gitignore` 에 넣어 두었다.

### 4.1 래퍼 결함 3건 — 전부 조용히 틀리고 있었다

`efficientad.py` 는 **테스트 0개, 실행 이력 0회** 였다. 돌려 보니:

| # | 증상 | 원인 |
|---|---|---|
| 1 | 양품이 0.665 로 전량 과검출 | `_adaptive_threshold` 가 항상 `None` — anomalib 2.x 는 `pixel_threshold` 를 노출하지 않는다. 정규화가 통째로 건너뛰어져 원시 맵이 그대로 점수가 됐다 |
| 2 | **양품·불량이 똑같이 0.639** | Lightning 모듈이 이미지별 min-max 정규화를 적용한다. 검출기가 눈이 먼 상태인데 숫자는 그럴듯했다. **내부 torch 모델(`model.model`)을 직접 호출**해야 한다 |
| 3 | 임계값 의미가 statistical 과 달랐다 | 점수 공식에 `0.5` 인자 누락 |

2번이 가장 위험했다. 성능 표가 정상으로 보이는데 검출은 전혀 안 되고 있었다.

### 4.2 결정적이었던 두 가지

**ROI 크롭.** 부품이 프레임의 1.8 % 라 640x480 을 통째로 256x256 으로 줄이면
15 px 결함이 6 px 가 된다. 이 상태에서 **모의 불량 24개를 전부 놓쳤다(0/24)**.
부품 바운딩 박스로 자르니 24/24 검출. `part_crop_box` 를 학습·추론이 공유한다 —
크롭이 어긋나면 점수 분포가 이동해 캘리브레이션이 조용히 무효가 된다.

**`model_size: medium` + 100 에폭.** `small` 은 **정규화 이전 원시 점수에서
이미 겹쳤다**(양품 0.397 > 불량 0.310). 어떤 임계값으로도 분리 불가능한
상태였고, 캘리브레이션으로 손댈 수 있는 지점이 아니었다. `medium` 으로
바꾸니 양품 최대 1.496 < 불량 최소 1.876 으로 갈렸다.

### 4.3 실촬영 학습 결과

| 항목 | 값 |
|---|---|
| 학습 | 82장 (**"1 2 3 4 5" 한 면 통일**) |
| 검증 양품 / 불량 | 21 / 19장 |
| **과검출 / 미검출** | **0/21 · 0/19** |
| 추론 | 약 60 ms (예산 1200 ms) |
| 분리 구간 | 양품 최대 0.431 · 불량 최소 0.541 |

**이상맵이 결함 위치를 정확히 지목하는 것을 육안 확인했다** — 부품 전체가
파랑인데 이물이 붙은 자리만 붉다. 성능 수치만으로는 "우연히 점수가 오른 것"
과 구분되지 않으므로, 이 확인이 있어야 신뢰할 수 있다.

### 4.4 ⚠️ 이 수치가 유효한 범위

**부품 1개 · 한 면 · 이물 1종(초록 테이프) 기준이다.** 다음은 전부 미검증:

- 다른 면 (도형 면, 인쇄 라벨 면)
- 다른 결함 종류 — 긁힘 · 눌림 · 얼룩 · 모서리 깨짐
- 다른 개체 (부품이 하나뿐이라 그 개체의 표면을 정상으로 외웠을 수 있다)
- **출하 부품 3종** — 실물이 없어 EfficientAD 체크포인트 자체가 없다

### 4.5 캘리브레이션 상수는 (모델, 데이터) 쌍에 종속된다

같은 상수를 다른 모델·데이터에 쓰면 조용히 망가진다. 세션 중 세 번 겪었다:

| 상수 | 문제 | 조치 |
|---|---|---|
| `safety_factor` | statistical 용 1.6 을 빌려 씀 → 불량 12/19 미검출 | efficientad 전용으로 분리, 스윕해서 **4.0** |
| `safety_factor` (재발) | small 용 0.7 → medium 에서 40장 중 25장 포화 | 재스윕 |
| `outlier_z_max` | 3.5 가 한 면 통일 후 정상 82장 중 11장을 제외 | **6.0** 으로 완화 |

**모델이나 데이터를 바꾸면 반드시 재스윕할 것.** 스윕은 원시 점수를 한 번만
채점하고 상수만 훑으면 되므로 재학습이 필요 없다.

### 4.6 검사와 치수 게이트는 분리되어 있다

결함은 실루엣을 바꾼다 — 모서리가 깨지면 재료가 없어지고, 이물이 붙으면
늘어난다. 그래서 치수 게이트는 **정확히 검사할 가치가 있는 부품을 거부**했다.
실측: 이물 붙은 부품이 폭 83 mm 로 읽혀(등록 62) 거부됐고, 빈 마스크는
`decide()` 규약상 1.0 — **부품을 본 적 없는 NG** 가 나왔다.

`segment_part(refuse_on_size_mismatch=)` 로 갈랐다. 포즈는 `True`(모델을 손에
정합하면 확신에 찬 오답), 검사는 `False`. 치수는 여전히 후보 **순위**를 매긴다.

### 4.7 부품별 백엔드

```yaml
# parts_local.yaml — .gitignore 대상이라 이 머신에만 있다
new_part:
  inspection_backend: efficientad
```

`inspection.backend_for(cfg, part_id)` 가 부품별 설정을 먼저 본다. 3종 부품은
체크포인트가 없어 `statistical` 로 남는다. **전역 기본값을 바꾸면 `make check`
가 GPU 를 요구하게 되므로 바꾸지 않았다**(§6 의 전제).

## 5. 자세 대칭과 성능 (2026-08-05 세션)

### 5.0 정지 부품인데 Yaw 가 180도씩 뒤집혔다

실카메라 15프레임 연속, 부품은 아무도 건드리지 않았는데 발행되는 Yaw 가
+20.6 과 -159.4 를 오갔다. fitness 는 전부 0.97~1.00. **어느 쪽도 틀리지
않았다** -- 형상이 180도마다 반복되므로 두 정합이 똑같이 잘 맞고, ICP 가 매
프레임 노이즈가 유리한 쪽을 골랐다.

`symmetry.canonical_pose` 를 `PoseBackend.run()` 에 넣어 대칭 등가 집합에서
대표 하나를 결정론적으로 고른다. 결과: Yaw 산포 347도 -> **3.1도**.

⚠️ **정규화는 모호성을 해결한 것이 아니라 감춘 것이다.** 부품이 실제로 앞뒤
뒤집혀 있을 수 있고 단일 시점으로는 알 수 없다. 파지가 대칭군에 대해 불변일
때만 안전하다 -- 이 부품은 **장축 중앙을 대칭 그리퍼로 잡으므로 무해**하다는
것을 확인받았다. 특정 끝을 기준으로 잡는 방식이 생기면 확신에 찬 오답을
넘기게 된다(ICD §6.1).

### 5.1 대칭은 측정해서 선언한다 — 추측하면 위험하다

`register_part.py` 는 `symmetry: []`(대칭 없음)로 등록한다. 실제와 다르면
`evaluate.py` 의 대칭 보정이 작동하지 않아 정상적인 모호성이 오류로 집계된다.

chamfer 를 ICP inlier 허용치(6 mm)와 대조해 측정한다:

| 회전 | chamfer | 판정 |
|---|---|---|
| 장축 90/180/270도 | 6.6~7.1 mm | 구분 가능 → **선언하지 않음** |
| 앞뒤 (+z 180도) | 5.42 mm | 구분 불가 → **선언** |

**구분 가능한 회전을 대칭으로 선언하면 진짜 틀린 자세가 "동등한 대안"으로
발행된다.** new_part 는 |G| = 2.

### 5.2 ⚠️ Roll 튐 — 미해결

Roll 이 ±90 / ±180 으로 여전히 튄다. 이것은 **대칭이 아니라 오답**이다:
chamfer 6.6~7.1 mm 로 형상적으로는 구분되지만 허용치 6 mm 에 근접해 depth
노이즈가 덮는다. 정규화로는 못 고친다. "위로 오는 면은 항상 같다"는 조건에서는
정답이 하나여야 하므로 실제 오차다.

### 5.3 장축 -8 % — 원인 확정, 해법은 배치

부품이 **롤러를 가로질러** 놓여 양 끝이 롤러 골 위에 뜬다. 그 부분은 스테레오가
시차를 못 풀어 **깊이가 아예 없다**(마스크 바깥 유사 색 픽셀의 72 %가 깊이 없음).

시도하고 **전부 무효**였던 것들 -- 같은 벽에 막힌다, 없는 깊이는 되살릴 수 없다:

| 방법 | 결과 |
|---|---|
| 컬러 스냅 cap 3 → 10 px | 장축 204.7 mm 불변 |
| `min_height_above_plane_m` 1~12 mm | 픽셀 수까지 완전히 동일 |
| 컬러 영역 성장 | 되찾을 픽셀 7개, 나머지는 평면 아래(롤러 골) |
| hole_filling | -8.1 → -4.0 % 로 절반 회복. 단 폭 +1.5 mm 부풀고 자세 의존 큼 → 미적용 |

**부품을 롤러와 나란히 놓는 것**이 가장 확실하다. 조사 중 자세가 바뀔 때마다
장축이 204 → 211 → 214 mm 로 움직인 것이 방증이다.

### 5.4 성능 — 병목은 GPU 가 아니었다

한 사이클 210 ms 의 내역:

| 단계 | ms | 장치 |
|---|---|---|
| **연결 성분 (라벨링)** | **58.7** | CPU |
| ICP 정합 | ~65 | CPU |
| EfficientAD 추론 | **6** | **GPU** |
| 나머지(평면·스냅·역투영 등) | ~25 | CPU |

**GPU 로는 크게 못 줄인다.** 신경망은 이미 GPU 에 있고 6 ms 다. 남은 것은
작은 배열의 순차·불규칙 연산이라 GPU 가 불리하다. Open3D 를 설치해 재 봤으나
정합이 67 → 65 ms 로 사실상 동일했다 -- 점군이 600 x 2000 이라 객체 변환
오버헤드가 이득을 상쇄한다.

실제로 줄인 것: **검사와 포즈가 같은 프레임을 각자 분할하던 것을 공유**로
바꿔 297 → 210 ms. 두 설정은 `refuse_on_size_mismatch` 하나만 달랐다.

다음 후보는 **연결 성분을 ROI 안에서만** 돌리는 것(~50 ms 예상, GPU 불필요).

⚠️ 택트 예산 1200 ms 에 현재 E2E 153 ms 다. **속도는 이미 병목이 아니다.**
CPU 전용으로 모든 테스트가 도는 설계 원칙(§7)을 깨면서까지 GPU 로 옮길
이유가 없다.

## 6. 실카메라 기하 — ROI·치수 (2026-08-05 세션)

### 6.1 부품 실측 치수 — **이 값이 없으면 아무것도 판정 못 한다**

```
new_part 실측:  장축 230 mm,  너비 49 mm,  높이 51 mm
```

세션 내내 "측정값과 등록값 중 어느 쪽이 맞느냐"를 판정하지 못했다. 등록값이
측정값에서 나왔으니 순환이었기 때문이다. 이 캘리퍼 값을 받고서야 오차를 축별로
분해할 수 있었고, 그 즉시 원인이 갈렸다.

**새 부품을 등록하면 반드시 캘리퍼로 재서 여기 적을 것.**

### 6.2 오차 원인 3종 — 전부 다른 곳이었다

최악 축 오차 **39.4 % → 2.7 %**.

| 원인 | 증상 | 조치 | 설정 |
|---|---|---|---|
| RANSAC 평면이 롤러 사이로 내려앉음 | 높이 +39 % | 롤러 윗면 재적합 | `support_surface.mode: "crowns"` |
| 뷰 병합이 합집합 | 높이 +16 % | 셀에 뷰 합의 요구 | `reconstruct(min_view_fraction=0.5)` |
| 스테레오 전경 비대 | 폭 +9 % | 컬러 경계로 안쪽 스냅 | `color_edge_snap.enabled` |

**롤러 컨베이어는 평면이 아니다.** 원통이라 보이는 표면이 꼭대기부터 옆면까지
연속 분포이고, 지배적 평면이 없어 RANSAC 이 옆면 중간에 걸린다. 기준면이 실제
지지면보다 약 20 mm 아래 잡혀 모든 높이가 부푼다.
`plane_distance_threshold_m` 조정은 **무효** (3~30 mm 훑어도 71~73 mm 로 불변).

**뷰를 많이 찍을수록 메시가 커졌다.** 병합이 합집합이라 극단값이 바깥으로만
자란다 — 1뷰 51.2 mm, 10뷰 59.4 mm. 모듈 문서가 "추가 뷰는 잡음을 평균할 뿐
형상을 더하지 않는다"고 적고 있었는데 셀별 높이에만 맞는 말이었다.

**성능은 함께 좋아졌다.** 스냅 도입 직후 뷰어가 1.2 fps 로 떨어졌는데,
원인은 알고리즘이 아니라 배선이었다 — 그래디언트를 후보마다 다시 계산하고
(후보 7.4개), 후보마다 640x480 전체에 형태학 연산을 돌렸다. 프레임당 한 번
계산 + 바운딩 박스 처리로 스냅 비용이 99.9 -> 4.8 ms 가 됐다. 곁들여
`imageops.gaussian_blur` 의 `np.apply_along_axis` 를 걷어냈다(2.3 -> 1.6 ms,
검사 백엔드도 같은 함수를 쓴다). 최종 **21.1 fps, 택트 172 ms**.

**컬러 스냅은 안쪽 전용이어야 한다.** 양방향을 허용하니 롤러의 금속 반사
경계로 끌려가 폭이 오히려 53.6 → 60.5 mm 가 됐다. 비대는 더하기만 하므로
바깥으로 옮길 이유가 없다.

### 6.3 카메라 배치가 검출을 좌우한다

| 지표 | 나쁜 배치 | 좋은 배치 |
|---|---|---|
| 광축 이탈각 | 13.1° | **1.7°** |
| **평면 위 최저 높이** | **9 mm** | **62 mm** |
| 검출 | 0/10 | 10/10 |

**최저 높이가 진단 지표다.** 부품 점이 벨트 바로 위(9 mm)까지 찍히면 옆면이
보이고 있다는 뜻이고, 그 점들이 평면에 투영되며 단면을 부풀린다. 윗면만 보이면
부품 두께에 가까운 값이 나온다.

⚠️ **ROI 중심은 실측값이다. 카메라를 옮기면 반드시 다시 재라.** 설계 추정값
`[0, 0, 0.60]` 은 실제 위치와 174 mm 어긋나 검출이 0/10 이었다.
확인법: `tools/live_view.py --source realsense --inspect` — HUD 가 상자 밖으로
몇 mm 벗어났는지 찍어준다.

## 10. 이미 겪은 함정 (반복하지 말 것)

| 함정 | 교훈 |
|---|---|
| 포즈 초기값을 카메라 쪽으로 배치 | 위치오차가 정확히 블록 두께(55 mm)만큼 발생. depth는 근접면만 보므로 중심은 관측면 **뒤** |
| 점수 정규화를 학습 분포 **폭**으로 | 학습 데이터를 늘리면 폭이 넓어져 불량이 임계값 아래로. **수준**에 고정할 것 |
| 검사 특징에 절대 밝기 사용 | 조명·노출·부품 위치 변화가 전부 "불량"이 됨 → median 밝기 정규화 필요 |
| 식별 로직을 `segment_from_config`에만 배선 | 백엔드는 `segment_part`를 직접 호출해 우회함. 양쪽 팩토리에 배선 필요 |
| 복원 중 크기 식별 활성화 | 치수를 정의하는 중인데 치수로 거르면 순환 논리. 복원·촬영 도구는 식별 OFF |
| `--level`이 보정항 오프셋까지 제거 | 부품 높이가 53.6 → 37.6 mm로 축소. 보정은 중심화해서 적용 |
| 창 닫힘을 `getWindowProperty < 1`로만 판정 | Qt는 예외를 던짐. 예외도 "닫힘"으로 처리 |
| 로컬 등록 부품이 출하 부품 허용치로 평가 | `locally_registered` 마커로 `--part all`에서 제외 |
| 치수 식별이면 다중 부품도 안전하다고 가정 | 뒤 부품도 치수가 **똑같이** 맞는다. 위치 게이트(스테이션 ROI)가 별도로 필요 |
| 문서의 status 값을 실행으로 확인 안 함 | ICD가 `NO_POSE`라 적힌 3개 경우가 실제로는 전부 `NG`였다. **파이프라인을 돌려봐야 안다** |
| 실측 정답 없이 알고리즘 개선 | 등록값이 측정값에서 나오면 순환이다. **캘리퍼 값부터 확보**할 것 |
| 평면 법선-광축 각도를 거꾸로 해석 | 0°가 "평면을 정면으로 봄"이다. 벨트를 내려다보면 0°에 가깝다. 반대로 읽어 멀쩡한 배치를 잘못됐다고 진단했다 |
| 오차를 한 원인으로 뭉뚱그림 | 축별로 분해하니 평면·뷰병합·비대 셋이었다. 하나로 보면 엉뚱한 처방이 나온다 |
| 이상점에 백분위 트림 적용 | 점이 고르게 분포한 표면은 트림 비율만큼 **체계적으로 줄어든다**. 합성 200 mm가 192 mm가 됐다 |
| 카메라를 옮기고 같은 설정으로 비교 | ROI 중심·치수가 전부 달라진다. **좋은 자세에서 프레임을 저장해 고정 데이터셋**으로 비교할 것 |
| 한 번도 실행 안 된 코드를 "있으니 된다"고 봄 | `efficientad.py` 는 테스트 0개·실행 0회였고 결함이 3건이었다. 전부 **조용히** 틀렸다 |
| 성능 수치만 보고 검출기를 신뢰 | 양품·불량이 **똑같이 0.639** 인데 표는 정상으로 보였다. 이상맵으로 **결함 위치를 눈으로** 확인할 것 |
| 캘리브레이션 상수를 다른 모델·데이터에 재사용 | (모델, 데이터) 쌍에 종속이다. 세션 중 세 번 깨졌다 — §4.5 |
| 검사기에 치수 게이트를 그대로 적용 | 결함이 실루엣을 바꾸므로 **검사할 가치가 있는 부품이 거부**된다. 빈 마스크는 1.0 으로 채점되어 진짜 NG 와 구분되지 않는다 |
| `del lst[:-0]` 로 캐시를 껐다고 착각 | `del lst[:0]` 이라 아무것도 안 지운다. 무한 캐시가 되어 벤치마크가 "절감 0 ms" 로 나왔다 |
| 대칭을 추측으로 선언 | 구분 **가능한** 회전을 대칭이라 하면 진짜 틀린 자세가 동등한 대안으로 발행된다. chamfer 로 재고 선언할 것 |
| 속도 문제를 GPU 로 풀려 함 | 신경망은 이미 GPU 에 있고 6 ms 였다. 병목은 CPU 의 연결 성분 58 ms 와 **중복 호출**이었다 |
| 학습 촬영 중 손이 화면에 들어감 | 한 장이 중앙값의 23배를 받아 기준값을 끌어올렸고, 그것만으로 불량 12/19 를 놓쳤다 |

## 12. ⚠️ 실행으로 발견한 미해결 결함 — 부품 미검출이 `STATUS_NG`가 된다

**증상**: 분할이 부품을 못 찾으면 `STATUS_NO_POSE`가 아니라 **`STATUS_NG`**가 발행된다.
ICD §3.1 권장 동작대로면 로봇이 **존재하지 않는 부품을 불량 배출**한다.

**실측** (파이프라인 직접 실행, `statistical` + `icp`):

| 경우 | `seg.ok` | 실제 status | ICD 표기(수정 전) |
|---|---|---|---|
| 벨트에 아무것도 없음 | False | **NG** (score 1.000) | NO_POSE |
| 치수 안 맞는 물체만 있음 | False | **NG** (score 1.000) | NO_POSE |
| 부품이 스테이션 밖에만 있음 | False | **NG** (score 1.000) | NO_POSE |

**원인**: 검사가 포즈보다 먼저 돈다. `inspection/base.py`의 `decide()`가 ROI가 비면
score 1.0을 반환하고(“조용히 OK가 되는 것보다 낫다”는 의도), 파이프라인은 그것을
불량으로 보고 포즈 단계를 건너뛴다.

```python
# roboworld_core/inspection/base.py
if not roi.any():
    return 1.0, np.zeros(anomaly_map.shape, dtype=bool)
```

**스테이션 ROI 이전부터 있던 문제다.** ROI는 같은 경로에 경우를 하나 더 추가했을 뿐.

**수정 방향**: `InspectionResult`에 "부품을 찾았는가"를 실어 파이프라인이
불량과 미검출을 구분하게 한다. `PartResult` 메시지 규격(ICD §3)은 바뀌지 않는다 —
`status`와 `message`는 이미 있다.

**결정 필요**: `is_good` 값을 무엇으로 할지. "부품 없음"은 양품도 불량도 아니다.
로봇 부서 회신 항목으로 ICD 체크리스트에 넣어 두었다.
